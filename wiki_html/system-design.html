Building systems that scale

System design is the process of defining the architecture, interfaces, and data for a system that satisfies specific requirements. Good decisions made early are hard to reverse — poor ones compound as systems grow. This page covers networking, databases, distributed patterns, and classic interview case studies.

CAP Theorem

In a distributed system, you can only guarantee two of three properties simultaneously: Consistency (every read returns the most recent write), Availability (every request gets a response), and Partition Tolerance (system continues operating despite network splits).

In practice, network partitions are unavoidable, so the real choice is CP vs AP. Examples: HBase/MongoDB (CP), Cassandra/CouchDB (AP).

PACELC Extension

If (Partition):
    choose between Availability (A) vs Consistency (C)
Else (normal operation):
    choose between Latency (L) vs Consistency (C)

Consistent Hashing

Both nodes and keys are mapped to positions on a hash ring. Each key is owned by the nearest node clockwise on the ring. Adding or removing a node only affects the keys in that node's immediate range — minimizing reshuffling. Used in Redis Cluster, Memcached, and distributed databases.

Two-Phase Commit (2PC)

Phase 1 — Prepare: Coordinator sends Prepare to all participant nodes. Each node locks resources and replies Ack.

Phase 2 — Commit: Once all nodes are prepared, Coordinator broadcasts Commit. If any node fails to prepare → Coordinator sends Abort.

!
Limitation: 2PC is blocking — if the coordinator crashes after prepare but before commit, participants hold locks indefinitely until recovery.

Chapter IV: Advanced Patterns

Circuit Breaker

Prevents cascading failures when a downstream service is unavailable:

  • Closed: requests flow normally; failures are counted
  • Open: after failure threshold exceeded, all requests fail fast — circuit "trips"
  • Half-Open: after a timeout, one trial request is allowed; if it succeeds, circuit closes

Rate Limiting Algorithms

  • Token bucket: each client gets tokens that refill at a fixed rate — allows short bursts
  • Leaky bucket: requests queue and are processed at a constant rate — no bursts, smooth flow
  • Fixed window counter: count requests per fixed window — simple but vulnerable to boundary bursts
  • Sliding window: smoother version of fixed window using rolling counts

Chapter V: Interview Case Studies

URL Shortener

  • Short code generation: hash the URL (MD5/SHA256, take first 7 chars) or Base62-encoded auto-increment ID
  • Storage: key-value store (Redis + persistent DB) — the mapping is a simple lookup
  • Redirect: 301 (permanent, client caches) vs 302 (temporary, every request hits server)
  • Scale reads with CDN/cache; writes are infrequent

WhatsApp / Chat System

  • Use WebSockets for persistent bidirectional connections between clients and servers
  • Message queues (Kafka) to buffer messages between chat servers
  • Fan-out for group chats: message broker distributes to each recipient's message queue
  • Push notifications via APNs (iOS) / FCM (Android) for offline users
  • Store messages in Cassandra (high write throughput, time-ordered reads per conversation)

Twitter / Social Feed Fan-out

  • Push (fan-out on write): on post, write tweet to every follower's timeline cache — fast reads, expensive writes for users with millions of followers
  • Pull (fan-out on read): on timeline load, query and merge tweets from all followed users — expensive reads, cheap writes
  • Hybrid: push for normal users; pull for celebrity accounts (too many followers to push to)

Uber / Ride Sharing

  • Location tracking: WebSockets (push model) from drivers → servers continuously
  • Ride matching: geohashing for fast proximity lookup; quadtree in Redis for range queries
  • Race conditions: mutex around ride matching logic; all actions transactional
  • Scale: Kafka for notifications, consistent hashing for data partitioning, read replicas for databases
